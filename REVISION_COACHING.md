# Contextual revision coaching

## Visible flow

Revision keeps Practice, Mock exams and History. Before submitting, Hint remains optional. After submission, the small secondary actions are **Explain**, **Ask**, and **Practise similar**. Mock exams expose coaching only after final submission. There is no new top-level AI destination.

Finishing a session shows a short recorded-evidence summary and one primary **Start recommended practice** action. A single mistake is explicitly insufficient to establish a pattern. The summary, its evidence and the recommendation persist in revision history. Starting the recommendation creates a real saved practice session; repeated clicks reuse that recommendation's attempt instead of duplicating it. It remains resumable when leaving the view.

## Evidence, patterns and scheduling

`RevisionCoachingService` calculates counts, patterns, next actions and progression from committed account-scoped revision records. These facts are not generated by a language model. Evidence spans current-version questions in linked banks in the same course/chapter (or just the source bank if no course exists). It excludes pending written grades, suspected key errors and immediate reinforcement when assessing independent performance.

A demonstrated recurring topic requires at least two recorded errors on different questions sharing an actual topic tag. Repeated errors on one question are described without inventing a broader topic weakness. Duplicate tags/records do not multiply the evidence. The summary cites saved session/question/version/timestamp references. Historical patterns are labelled as recorded history, not a new diagnosis or an assertion of present mastery.

The answer, an explicit later-review reminder, archive record, and completed-session recommendation are saved together in the existing SwiftData transaction. An immediate correct retry retains later-review eligibility. The recommendation selects actual eligible questions, prefers unresolved/due questions, and stays within the stated topic where available. It never fabricates or silently generates an activity. Before launch, current account, source session, key-review flags and question versions are checked again; edited questions cannot inherit stale recommendations.

## Gradual difficulty

Relative levels are anchored at 3 for existing teacher/source questions and stored with generated questions. Marks, response speed and question length are not treated as measured teacher difficulty. Changes are bounded to one step from the current bank's relative level, even with mixed-level history.

Two independent errors on different questions support one more scaffolded step. Four unassisted correct attempts across at least three questions and two sessions, at the current level or above, support one step up. Hinted answers, immediate retries and pending writing cannot establish this success. With insufficient evidence the current level stays unchanged. Bounds are 1–5. The level guides optional new similar questions; original teacher wording/marks are never rewritten to simulate difficulty.

## Provider and sources

`RevisionCoachingProviding` uses the existing configured `AIRevisionAssistantClient`, its selected provider/model, readiness checks and source-bound contract. Credentials and provider selection are unchanged. Coaching skips the older shared AI history log: private answer prompts do not enter that account-unscoped log.

Context contains the saved question snapshot and key/model answer, actual submitted answers/results, linked course notes, readable local PDF/text passages retrieved through the existing resource pipeline, and related imported teacher examples. Only linked course/chapter sources are included. Unreadable/unsupported resources fall back to explicitly labelled saved descriptions when present; they are never represented as file contents. Teacher examples guide language, format and relative challenge. Supplied passages and requests are untrusted data, not application instructions.

Explain/Ask request structured, source-bound feedback about the specific submitted answer. Multiple-select input includes the actual missing/extra selections; numerical or written reasoning is not invented when the student has supplied only a final answer. Unknown source IDs are rejected. Written feedback is labelled provisional and cannot award official marks. A suspected key conflict adds a review flag/reason and is excluded from coaching evidence/recommendations; the stored objective key, score and correctness stay authoritative and unchanged.

AI text remains provisional assistance, not a verified replacement for the teacher's material. Counts, schedules, grades and activity launches use application data and validation rather than model claims.

## Similar-question preview and provenance

Practise similar opens an optional preview. Drafts support existing question types. Rubric-based/extended written responses must use written review, not automatic exact-string grading. The student can edit prompts, keys and explanations, discard drafts, inspect cited sources and acknowledge reviewing the preview. Raw/malformed responses and invented source IDs are never saved as questions.

Only **Save reviewed questions as AI practice** writes a separate AI bank. Saving is transactional and idempotent by preview ID. Draft IDs are never reused as persistent question IDs, so a provider cannot overwrite a teacher question by returning its UUID. Original teacher banks remain separate.

The account-scoped generation record stores provider/model, generation time, prompt version, difficulty and evidence reason, source bank/session, actual attempt references, source IDs/titles/references/content hashes, original preview, reviewed questions, and the mapping to saved question IDs. Sources/provenance can be inspected in the preview and saved bank setup. No provenance is fabricated for older AI banks that did not retain it.

## Availability and verification

Ordinary grading, hints, persistence, schedules, deterministic summaries and recommended practice require no AI request. Failure/unconfigured providers leave the recorded correction and existing practice available. Async requests cancel on navigation/account changes and check account identity again before returning/saving data.

The focused suite uses fixture providers, not external requests. It covers the complete answer → committed attempt → review update → evidence-based recommendation → saved recommended-practice chain, idempotent launch, sparse versus repeated evidence, cross-bank patterns, gradual progression including mixed-level history, edited questions/account boundaries, key flags with unchanged grades, actual linked-file excerpts, fabricated-source rejection, provider failure, generated question formats/written review, mandatory preview, stored provenance and protection against teacher-ID collisions. Existing Exam Lab, history, question-bank and topic suites also run.

Final regression result: **43 unique tests passed**. The built app's real UI was checked with `--exam-lab-validation` in a disposable in-memory Biology workspace: submit an incorrect answer, finish, inspect the single-mistake summary/evidence, start the recommended Transport practice, leave it and confirm it remains in Continue an attempt. No production study records or live external AI calls were used for verification.

All new fields/payloads are additive; no SwiftData schema change or destructive migration is required. Revision history and generation provenance remain local to this Mac, under the existing account identity, and are not added to cloud sync in this change.
